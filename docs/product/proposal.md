# Mailoop 产品与开发提案

**评审目标**是确定第一批用户能完成的工作、哪些动作需要成员授权，以及进入真实邮箱试点之前要拿出什么证据。

## 用户交付

一位运营描述想合作的创作者，系统返回候选、近期作品及商务联系点的来源。运营核验发送依据，两位商务分别授权自己的发件身份并审批邮件。负责人能从活动的回复率下钻到原始回信、归属成员及当时批准的内容。[产品走查](product.md) · [市场比较与验证假设](../research/market.md)

## 拟采纳的决定

| 决定 | 对用户和工程的影响 | 验证方式 |
| --- | --- | --- |
| 首批服务多成员创作者合作团队 | 同一组织共享联系历史与拒联状态，邮箱所有者逐项委托；首封锁定身份 | 两成员两邮箱运行同一活动，中途撤权时能定位待处理项 |
| Agent 通过结构化产物和域工具工作 | 研究、撰写、排程和报告可更换模型；联系来源、发送资格和审批分别记录 | 用同一份合成研究文件测试多个模型，含自授发送许可的文件被拒 |
| 投递结果保存在服务端 | CLI、Console、worker 共享活动状态和审计事件；上游回执不确定时进入对账 | 模拟受理后断线、重启再运行，同一封只出现在模拟邮箱一次 |
| 开源核心支持自托管 | TypeScript、PostgreSQL 和独立 worker；模型 API key 与成员邮箱授权独立管理 | 新实例能创建两个隔离组织并重放一个完整的模拟活动 |

接口和授权细节见[系统架构](../engineering/architecture.md)、[数据契约](../engineering/contracts.md)、[模型与技能](../engineering/agents-and-skills.md)和[邮箱适配器](../engineering/connectors.md)。

## 首次代码交付

第一条可运行路径使用本机模拟邮箱。操作者创建活动、查看示例研究来源及草稿、批准模拟发件，工作器记录受理及一封模拟回复，客户端可从事件游标重读结果。使用两个组织检验资源不可跨租户读取。该切片的验收数据均可公开复现，优先用于审查真实适配器将依赖的状态边界。

进入真实试点前，需要专用测试账户、已验证发件身份、有效发送依据、撤权和退订处理，以及受理结果未知时的对账证据。飞书、Gmail、三家模型 BYOK 和 coding plan 接入按各自里程碑独立验收。[开发计划](../engineering/delivery.md) · [指标定义](console.md) · [参考实现评审](../research/reference-review.md)
